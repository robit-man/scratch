Room security + persistence

The URL fragment is the key. The value after # is never included in HTTP requests. This page hashes it to create a rendezvous room name and separately derives an AES-256-GCM application key from the original fragment.

Network payloads are therefore protected by WebRTC transport encryption and application-layer encryption. File names, CRDT document updates, cursor presence, edit history, asset metadata and file bytes are encrypted; signaling sees only a hash-derived room identifier and transport metadata.

Anyone with the complete link can read and modify the room. Use the generated high-entropy room URLs rather than short human passwords. This is capability-based access, not an account system.

No central archive exists. Each browser keeps an encrypted local cache. A new browser can recover the current state only while at least one peer that already has that state is online. Large files are transferred peer-to-peer and are not uploaded to this host.

Live media is ephemeral. Microphone, camera, and screen-share tracks travel directly over WebRTC/SRTP and are not stored in the scratchpad cache. Screen sharing asks the browser/OS chooser to offer system audio when supported; the browser and operating system decide whether that source is actually available.

Room QR code

The QR contains the complete room URL, including the fragment secret. Anyone who scans it receives full read/write access to this room.

Synchronized edit history

Recent edit bursts are part of the encrypted CRDT state, so peers converge on the same history even after reconnecting.
